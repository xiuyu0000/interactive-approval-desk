# Designing Review Items (v3.3, updated v3.4, v3.7 and v3.7.1)

Moved here from SKILL.md in v3.6 without changes, except where noted (v3.6). v3.7 adds the section "Low Reading Load" below (its points are numbered L1–L8, so "point 6" always means the cold read in this first list) and changes points 6 and 9.

Reason: in R08 of project B’s requirements interview, the reviewer rejected cards like "编号 / 内容 / 是否推断" tables: several unrelated decisions were squeezed into one item, each row was a compressed fragment without scenario, reason or consequence, and headers such as "是否推断" or cell notes such as "后一半是推断" had no clear meaning.

1. **Pick the card type from the shape of the pending information.**
   | Information | Card | Reviewer action |
   |---|---|---|
   | Several related propositions to confirm (inferences, rule wording, fixes) | `kind: "group"` — topic card with points | Each point starts undecided ("待你表态"); reviewer clicks 同意 / 要调整 / 不同意 on each (click again to undo). Any choice opens a note box — optional for 同意, asked for 要调整 / 不同意. "其余 N 点都同意" fills the remaining points in one explicit click and labels them. The card counts as answered only when every point has an answer |
   | Pick one of several alternatives | `kind: "choice"` | Clicking an option is the answer; "都不合适，我在评论里说" for none |
   | Pick any number of alternatives | `kind: "multi"` | Tick options, then 通过 / 待微调 / 需修改; 通过 with nothing ticked takes the recommended ones |
   | Facts only the reviewer has (dates, names, counts) | `kind: "fill"` with `fields: [[id, label, placeholder]]` | Type into inputs; any filled field counts as answered |
   | A single statement to accept | `kind: "confirm"` | 通过 / 待微调 / 需修改 |
   Tables are only for reference material (comparisons, schedules), never as a container of decisions.
2. **Group card fields**: `context` (what problem this topic solves, and what happens if all points are accepted), optional `example` (a concrete story when the context is too large to state abstractly), optional `settled` (already-decided background, shown without controls), optional `view` (sandbox view id), and `points`. Each point: `id` (unique within the card; the answer is stored under it), `title` — the full proposition in plain words, one decision only (split sentences joined by "；"; put incidental fixes in their own point marked "（顺带改正）"); `src` — `你已定` / `推断` / `冷读` / `建议`; `target` — which document changes (`改基线` is highlighted); `ifNo` — always: what happens if rejected or what the alternative is; `why`; `risk` when there is one; `ex` when the rule is abstract; `text` (原文与落点, collapsed) only when the exact wording is itself being approved or the reviewer may need it.
3. **Link the sandbox only when one existing view can show the whole context of the group** (e.g. a flow view that contains every object the points talk about). Otherwise omit `view`; do not link a view that shows only part of the story. (v3.7.1) Whether the round has a sandbox at all is decided first (`page-and-export.md`, "When a Round Gets a Sandbox"). The link is the "🗺️ 在沙盘里看全貌" button in the card head, on every card kind. A `view` that names no existing view gets a lint warning instead of a silently missing button.
4. **Hover over hunting**: glossary terms are auto-linked (first occurrence per card, `adLinkTerms`). List homonyms that mean something else on this page in `TERMS_NOAUTO` (e.g. "评审" meaning prototype review rather than the overdue-review meeting). Keep codes out of titles and body text — use the Chinese name, add the code in brackets only when needed, and put code-heavy wording in the `from` line or in `text`. Codes that remain must still resolve in `CODES` (SKILL.md, Core Design Philosophy, principle 5).
5. **Weight**: set `weight: "heavy"` (changes the baseline, scope, permissions, data outflow or schedule) or `"light"` (restating the reviewer's own decisions, pure division of labour) so the reviewer knows where to slow down.
6. **Approver cold read before publishing, in two passes (v3.7)**: dump the page (`node <skill>/round_template/dumptext.js <out.txt> [Rxx]`). The dump has two passes: what is visible with every fold closed (page brief, the sandbox — title, lead, views, the open view's spotlight text and the object table, or how-to step 2 as the page shows it ("这一轮没有沙盘" with the `NO_SANDBOX` reason, or "这一页没有写为什么") (v3.7.1) — then the route, each card's four boxes, pictures and options), then everything opened plus every sandbox view's spotlight text and links (who connects to whom, with which label and card), then the hover texts, which now include codes from the sandbox, the object table and the route. Give it to a subagent playing a busy approver who has not read the source documents. Pass 1 only: per card, it must say what is decided, what is recommended, what is given up, what happens on disagreement, and its own answer with a confidence. Then pass 2: if any of those answers or the confidence changes, the fact that changed it moves up into the visible layer. Also ask what is unclear, missing (example, consequence, risk), noisy or mis-grouped, and (v3.7.1) whether the sandbox shows the structure the cards rely on or, on a round without one, whether the `NO_SANDBOX` reason holds. Revise until no card blocks a decision and pass 2 changes nothing. Let this read decide which fields each card needs.
7. **Layout**: long page with a sticky left table of contents (`#toc`) showing every item with a status dot (half-filled dot = group partly answered) and a "→ 下一个待表态" button; hidden under 1000px width. The reviewer can hide it ("隐藏 ⟨" in its header or "⟨ 隐藏总览 / ☰ 显示总览" in the filter row) to widen the cards; the choice is remembered per viewer in `localStorage` (`{PROJECT}/{KEY}-toc-hidden` since v3.6, `{KEY}-toc-hidden` on pages without `PROJECT`; wrapped in try/catch).
8. **Restructuring a published round**: if item meanings change after publishing, bump the localStorage key to `{ROUND}-feedback-v2` (the data's `KEY`; since v3.6 the page stores it as `{PROJECT}/{ROUND}-feedback-v2`, and a hosted draft saved under the old key is ignored) so stale answers are not applied to different questions; keep the db path `feedback/{ROUND}`.
9. **Fold the explanations, keep the decision visible (v3.4; v3.7: with a `brief`, `plain` / `context` / `evidence` / `example` / `risk` / `settled` / `fig` / `tables` and folded pictures fold into 核对材料 automatically, so a risk that changes the decision goes into ③ or ⚖ as well; diff-style points put 完整说法 · 理由 · 要注意 · 场景 · 不同意的话 · 原文与落点 into one 细节 chip on the answer row, marked "含 ⚠️ 要注意" when there is a risk, so their must-not-miss cost goes into `lose`)**: on each point only the proposition (`title`, in a larger bold line), its tags and the answer buttons are always visible. 场景 (`ex`), 理由 (`why`), 要注意 (`risk`), 不同意的话 (`ifNo`) and 原文与落点 (`text`) are folded behind one chip each and open individually; the group-level `example` and `risk` fold the same way, while `context` and `settled` stay visible. Each kind has its own look so the eye can tell them apart: 场景 serif text on a blue tint, 理由 plain text on grey, 要注意 an amber chip that stands out even while closed and an amber panel, 不同意的话 small grey text in a dashed box, 原文与落点 small text on a gold tint. A "📖 展开全部说明" filter button opens everything for reviewers who want to read it all. Because the details are hidden by default, the `title` must be decidable on its own for a reader who opens nothing; put what they must not miss in `risk` (its chip is highlighted).
10. **Inputs (v3.4)**: every textarea and text input uses the shared field style (light fill, 10px radius, accent focus ring) and grows with its content; point note boxes carry a coloured label matching the answer (补充说明（可选） / 希望怎么调整 / 为什么不同意).

## Low Reading Load (v3.7)

Reason: in project A R03 the reviewer said the cards had full context but far too much text, and reading them was the main source of approval pressure. R03-02 showed about 3,900 characters before its options (about ten minutes for one decision); across the real rounds measured, the cards of the newer rounds averaged 600–1,000 visible characters. "Decide from the card alone" (principle 6) had turned into "read everything on the card", because the template only offered paragraph slots. v3.7 keeps the whole record on the card but splits it into a short visible layer and folds. Field shapes and limits: `round_template/README.md`, "v3.7 低负担字段"; working example: `round_template/sample/data_r01.js`.

L1. **Two layers.** The visible layer lets a reviewer who trusts the analysis decide in about a minute; the folds let a reviewer who does not verify it. A fact that would change the decision (a precondition, an admission against the recommendation, a cost, a threshold, a dependency) must be in the visible layer. A fold may only hold its support.
L2. **The four boxes (`brief`)** go on every heavy card and on any card that would exceed its budget:
   - `ask` ① 你在决定什么: the question in one line, naming the options when there are few.
   - `rec` ② 我推荐 and `cost` ③ 你会失去什么: drawn side by side at the same size, so the recommendation never stands without its price. `rec` without `cost` fails the lint. `lose` names what is given up as short items; an item with its source is a nested pair (`lose: [["拆解只对高风险任务做", "R03-05 第 4 点"], …]` — a flat `["拆解只对高风险任务做", "R03-05 第 4 点"]` would be two losses, and the lint fails a string item that starts with a code). Never name a loss by code alone, and write `lose` only together with `cost` (the items are drawn inside ③). With a brief, `risk` is folded: a risk that would change the decision goes into `cost` or `honest`.
   - `honest` ⚖ 实话: required when the recommendation is not what the reviewer's own priority order gives, when you are least sure of it, or when a precondition can flip it. Keep the admission as plain as in the prose ("严格按你的顺序，该选 A"), and name the criteria and the judgment the recommendation rests on, not just "a judgment you may reject". Use the same scope words in `honest` and `cost`: if the cost is about 前七点, the admission says 前七点 too, not 每一处.
   - `ifno` ④ 不同意会怎样: what happens, or the path to the other answer.
   - Give a box `basis` (按文本数 / 实测 / 你已定 / 设计差异 are facts; 我的判断 / 估计 / 预期 / 推断 are judgments) when the reader needs to know which it is; expected benefits are 预期, never 按文本数. Give it `more` when the full paragraph belongs right under it.
L3. **Pictures before paragraphs.** At most two pictures are visible (`vis`); further ones get `fold: true`. Choose by the shape of the information, and let the template draw it; never hand-write SVG, HTML tables or coordinates for a card.
   | Information | `type` |
   |---|---|
   | Two options compared criterion by criterion, in the reviewer's priority order | `versus` |
   | Conditions under which the answer changes | `tree` |
   | One numeric threshold (with the reviewer's own input named in `ref`) | `scale` |
   | Steps; what happens after a choice | `flow` |
   | Who does what, in what order | `seq` |
   | Structure before and after; what two options share and where they differ | `layers` |
   | Quantities | `bars` |
   | Which things the whole round is about, who produces, changes or can see them, how they flow | not a card picture: the round's sandbox (`OBJ` with `FLOWS` or `PANO_EDGES`; `page-and-export.md`, "When a Round Gets a Sandbox") |
   - (v3.7.1) A card picture shows this card's own decision. When several cards would draw the same objects or actors as `layers`, `flow` or `seq`, draw them once in the sandbox, keep only each card's slice in its picture, and link a card with `view` when one view shows its whole context (point 3). On a round with neither a sandbox nor `NO_SANDBOX`, the lint warns and names the cards that use these three types.
   - Show both sides. A one-sided picture (only the recommended option's numbers) never sits next to the recommendation.
   - A number appears only with its counting rule and every condition it depends on, in the same visible block (`bars` requires `cap`; "73 → 30" must say "R03-05 前七点都同意" and also "第一个增量起就要用则 51"). The number-source lint fails any number of two or more digits in the visible layer that does not appear in the card's folded prose (codes such as R03-05 are ignored; a visible number on a card with no folded prose at all fails too).
   - In `versus`, say which two options are compared: on a card with options, write `keys` (or start each `sides` name with the option key); the lint fails a comparison it cannot map. Mark the reviewer's own criteria with a `"you"` band; the template states the first of them that separates the options. The honesty lint checks every `versus`: if any cell of that first separating row favours an option you do not recommend — even when the row is split — `honest` is required.
   - A caption says what the picture shows, never what to choose. No scores, totals or weights; mark rows that measure the same thing with `≡` and explain them in `same`.
   - Mark only the goal mappings the source states (`goal` on a point, `bands` with `"you"` in `versus`); an inferred mapping is your judgment and goes into the text with 推断.
L4. **Options carry both sides.** In object form every option has `k`, `t`, `up` and `cost` (the lint wants both or neither), `then` (what happens after, with hedges such as 没有实测 kept), `fx` (its effect on other cards, written out as pairs: `fx: [["R02", "关闭：待定项并入本轮"]]`; the route and the affected card show it), and `undo` when backing out is possible. Give `then` and `undo` to every option that has them, not only to the recommended one (the lint warns when only the recommended option has them; take the way back from the source, e.g. another card's fallback rule, rather than inventing one). The original description goes into `more`. Consequences never live only in a hover title or a glyph: phones have no hover.
L5. **Group points as diffs.** For a group that changes existing practice, write each point as `area` + `from` → `to`, with `lose` for what agreeing gives up. Add `sub` for scope qualifiers that must not get lost (the three triggers, "发布前的试用仍用另一家", the reviewer's own earlier words). Add `no` whenever disagreeing does not simply keep the left side, and `labels` when the left side is not current practice. Add `needs` for prerequisite points (they turn red live when that point gets 不同意), and `unsure` for the points you are least sure of. Keep `title` as the full proposition: it is folded under 细节 and used in the export. Write every point of the group this way and give each its `src` (the legend states the majority source once; the lint fails a group that mixes diff and plain points). A note that applies to several points goes on the first of them once ("连带：第 1、2 点……"), not on each. Set `bulk: false` on a group whose points trade away the reviewer's own priorities; the card then has no "都同意" and the header one-click skips it.
L6. **Move, never cut.** When a card gets a `brief`, keep `plain` / `context` / `evidence` / `example` / `risk` unchanged; the template folds them into 核对材料, and the export still carries them. Put reference tables in `tables`, not in hand-written `fig` HTML, and write their cells in HTML (`<b>`, `<br>`, `<small>`): the page does not render Markdown. Do not delete or water down prose to meet a budget; restructure the visible layer instead.
L7. **Budgets are part of the test.** `test.js` counts what is visible with every fold closed (Chinese characters and Latin words; buttons, header chips and fixed labels excluded; picture text — including the generated goal map — counted separately): 700 / 480 / 300 per heavy / normal / light card, groups 340 / 280 / 220 plus 80 / 70 / 60 per point, at most 340 per visible picture, plus a limit per box and label (all in `AD_LIMITS`; table in `round_template/README.md`). Over budget means not passed. Decision facts outrank the budget: when they do not fit, split the card in two; never cut them or move them into a fold. `BUDGET: "warn"` in the cfg turns only these checks into hints — budgets, legibility (font size, contrast), the 375 / 360px overflow and (v3.7.1) the two sandbox canvas checks (a box or label off the canvas, label text wider than its label) — and is only for rebuilding older rounds; lint errors (shape, honesty, number source) fail either way.
L8. **Page level.** Decide the sandbox first (`OBJ` with `FLOWS` or `PANO_EDGES` for a round about structure; otherwise a one-line `NO_SANDBOX`, v3.7.1). Give the page a `BRIEF` (你要定 / 我的结论 / 实话 / 前提, one line each, plus 最要细看 when one card needs the slow read); the long `LEAD` is then folded, so anything the lead says the reviewer must know goes into a `BRIEF` row. The 审批路线 (at the top of STEP 3, right before the cards, since v3.7.1) is generated from the cards: kind and count, weight, recommendation (`brief.tag`; without it the recommended option, then the first clause of ②, then "只有你知道" on fill cards), the first clause of `honest`, prerequisites (`needs`) and option effects (`fx`), minutes and status. Write `honest` so that its first clause stands alone.
